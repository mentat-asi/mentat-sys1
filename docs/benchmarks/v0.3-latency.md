# Experimental v0.3 inference acceleration

On one NVIDIA A800 80GB PCIe, the experimental v0.3 runtime measured
**21.47 ms for one field** and **40.66 ms for three fields**, including
localhost HTTP and response parsing. The single-field mean is about one
seventh of TypeSafe's official **150 ms** latency reference. These are
different deployments and measurement conditions, not a matched speed test.

This records v0.3 runtime measurements from 2026-10-18. The implementation
is now available through `mentat-sys1-v03`; see the
[inference guide](../inference-v0.3.md). Model weights are available at
[yunqu/mentat-sys1-v0.3](https://huggingface.co/yunqu/mentat-sys1-v0.3).
These local measurements do not establish an official JevBench rank.

## What changed

The model checkpoint, prompts, candidate ordering, unknown option, per-type
temperatures and FP32 decision readout are fixed. The candidate changes how
the forward computation runs:

1. **Merge LoRA in GPU memory.** Merge the frozen adapter into the BF16
   backbone for inference, removing separate adapter matrix multiplications.
   Original on-disk weights are unchanged. BF16 merging changes rounding.
2. **Batch fields.** The earlier reference runtime runs one forward per
   field. The batched candidate runs independent fields as rows of one
   forward, with right padding and a readout at each field's real final token.
3. **Use fast kernels and CUDA Graphs.** FLA Triton kernels implement the
   causal convolution and chunk gated-delta computation. CUDA Graphs replay
   warmed shapes; direct text tokenization avoids repeated multimodal
   processor and codebook work. Boundary, context and code/token checks are
   retained. Unseen graph shapes use eager execution.
4. **Share a prefix within each request.** Find the identical token prefix
   across fields, round its length down to a multiple of 64, and use it when
   at least 128 tokens can be shared. Compute the prefix once, expand its
   attention/conv/recurrent state into independent field rows, then compute
   the suffixes as a batch. Every request computes a fresh prefix. There is
   no cross-request KV cache or answer cache.
5. **Fuse pointwise operators.** `torch.compile` fuses RMSNorm, gated RMSNorm,
   and SiLU/multiply operations, with explicit precision casts preserved
   (`emulate_precision_casts=True`). The stable accumulation setting remains
   `allow_bf16_reduced_precision_reduction=False`.

The three-field ticket has 993 actual input tokens across its prompts. It
shares 256 tokens, reducing computation to 481 tokens before padding:
256 shared tokens plus 225 suffix tokens. The warmed graph computes 508
tokens after padding, versus 1,020 for the earlier full batch. The prefix
candidate uses two backbone phases, which together do less work than the
single full-batch phase. Gains depend on prefix length and workload.

Zero generated answer tokens and the separate decision readout were already
features of the original runtime; they are not new optimizations here.

## Measured latency

Each scenario uses 20 warmups per trial, three trials of 200 timed requests,
one outstanding request at a time, and four CPU threads. All trials are
retained. Times are warm; model loading, merging, compilation and graph
capture are excluded. Baseline runs used the same physical A800 earlier the
same day, rather than interleaved trials.

| Runtime | One field HTTP mean | Three fields HTTP mean |
| --- | ---: | ---: |
| Native v0.3, sequential fields | 83.60 ms | 249.86 ms |
| Earlier batched/merged candidate | 25.70 ms | 63.38 ms |
| Shared prefix + pointwise fusion | **21.47 ms** | **40.66 ms** |

The final candidate reduces three-field latency by **35.84%** versus the
earlier accelerated candidate. HTTP P95 is **21.85 / 41.28 ms** for one/three
fields. Server means, excluding HTTP/JSON overhead, are **20.30 / 39.33 ms**.
Forty requests with changing ticket IDs averaged **40.34 ms** over HTTP;
each request executed fresh model computation.

## Jev references: keep the timing definitions separate

TypeSafe's [official use-case map](https://docs.typesafe.ai/concepts/use-case-map)
quotes **150 ms** for real-time applications. Its
[launch article](https://typesafe.ai/blog/introducing-system-one-models-and-jev)
gives **70–500 ms end-to-end** and says published evaluations generally run
from West Coast laptops near its service. The 150 ms statement does not
specify the request, question count, hardware, sample count or percentile.

Our **21.47 ms localhost single-field mean is approximately one seventh of
that official 150 ms reference** (150 / 21.47 ≈ 6.99). This is an illustrative
comparison of published numbers. A local call does not include the remote
network path, and the workloads and measurement boundaries are unmatched.
It does not demonstrate a measured 7× or 7.5× model speedup over Jev.

There is also a more specifically documented historical measurement:
[StartLux's pinned inference report](https://github.com/StartLuxLabs/StartLux-Decision/blob/a9101e918e097b26fea5ead9ed893b823e875e46/docs/inference.md)
sent each of these ticket scenarios to Jev 1.13 100 times on 2026-09-29.
It reports gateway `x-envoy-upstream-service-time`, rather than client
round-trip time:

| Scenario | Our server mean | Historical Jev server mean | Reference ratio |
| --- | ---: | ---: | ---: |
| One yes/no field | 20.30 ms | 63.5 ms | 3.13× |
| Three fields | 39.33 ms | 64.0 ms | 1.63× |

Jev's deployment hardware is unspecified; neither comparison is a fresh
matched Jev run. The historical report's approximately 330 ms remote client
time is not used as a compute-speed baseline.

## Numerical quality

All seven public Intern-Decision suites were evaluated against the same
frozen native v0.3 output cache: **12,351 fields**, with no missing or invalid
outputs. Numerical variants can change probabilities and borderline choices.

| Metric | Native v0.3 | Earlier accelerated | Prefix + fusion |
| --- | ---: | ---: | ---: |
| Seven-suite ID mean ↑ | 89.5942% | 89.5318% | **89.5209%** |
| Typed soft-label Brier ↓ | 0.0540300 | 0.0542541 | **0.0543281** |
| Public JevBench correct / 231 ↑ | 204 | 204 | **204** |
| Winner agreement with native | 100% | 99.7490% | **99.7571%** |

The final candidate changes 30 of 12,351 winning choices, and the mean ID
decreases by 0.0733 percentage points versus native. Full per-suite scores
and probability deltas are in [summary.json](v0.3-latency/summary.json).
This is reused public validation that informed model iteration, not an
independent leaderboard result. The Intern bundle's Jev reference is 88.74%
ID and 199/231; it is a different published evaluation from the official
Public-231 aggregate used for the historical v0.2 release.

Prefix-specific checks attempted 80 constructed multi-field requests;
78 had eligible prefixes. Across their 234 fields, shared-prefix versus
full-batch inference under the fused runtime changed no winning choices;
the maximum probability difference was 0.01234. An A/B/A graph replay check
returned exactly the same A output after a different request B.

The original native v0.3 DI is 52.15 on accessible tasks (strict abstention:
52.07), with HLE unmeasured and its contribution kept at zero. The
accelerated runtime has not rerun DI. Jev's published 57.91 has different
coverage, so latency and ID do not establish overall superiority.
